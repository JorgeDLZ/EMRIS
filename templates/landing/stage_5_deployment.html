Deployment

How the trained models are stored, served inside the application and used by each role.

Saved models and preprocessing
  • Each trained component is saved whole: for the impact estimator, the scikit-learn Pipeline with its encoders and model, together with its tuned threshold. It is serialised with joblib (compression level 3) and stored in the database, so it survives redeploys of the free Render service, which has no persistent disk.
  • Every version is one row with its component, version number, metrics, training period, number of rows and the versions of the libraries it was trained with. Every prediction stores the version that produced it.
  • Models are loaded only when first needed, and only the active version of each component is kept in memory by each process.
Demonstration in the deployed application

The course suggests a small Flask application to demonstrate the model. EMRIS replaces it with the deployed Django application itself: reporting a new emergency (Report emergency) sends its inputs to the active models, and the estimate, its factors and the municipal risk level appear on the emergency at once. The reasons are one stack and one deployment, a model that already lives inside the information system it was built for, and no second service to run on the free tier.

Dependencies are pinned in requirements.txt: Django 5.2, scikit-learn 1.9.1, pandas 3.1.1, NumPy 2.5.4 and joblib 1.6.0, among others. To run it locally:

  1. Create a virtual environment and run pip install -r requirements.txt.
  2. Copy .env.example to .env and set DEBUG=True.
  3. Run python manage.py migrate.
  4. Load the data with python manage.py load_baseline and python manage.py load_seismic.
  5. Train the first models with python manage.py train_initial.
  6. Create an administrator with python manage.py createsuperuser and start the server with python manage.py runserver.
User instructions and integration
  • Operators report an emergency; its estimated probability, main factors and municipal risk level appear on the emergency. When they record the impact, the emergency gets its profile. When they draft the action plan, “Suggest plan” shows the most similar past cases and lets them add the suggested actions, which they can edit.
  • The emergency list shows the open emergencies first, ordered by estimated probability, so the ones most likely to be high impact are seen first. Operators, risk managers and administrators also see the municipal risk ranking on the dashboard.
  • Risk managers and administrators approve the plans and close the emergencies.
  • Action owners see the emergencies where they own an action and update those actions.
  • Administrators manage the models on the Models page: metrics, retraining, rollback and monitoring checks.

The information system the models are integrated into is EMRIS itself: every report stores its predictions with the model version that produced them, so the integration is part of the daily workflow rather than a separate tool.

Monitoring, incidents and feedback
  • A failed prediction never blocks saving an emergency: the error is logged and the emergency shows “Prediction unavailable”.
  • A failed training run is recorded on the Models page with its reason, and the active models stay in place.
  • Incidents are reported to an administrator, who checks the Models page and the Render logs.
  • Feedback: users correct a suggested plan by editing it before approval, and every closed emergency with a recorded impact becomes training data for the next retrain.
